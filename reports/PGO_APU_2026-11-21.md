# Optional build variants: PGO, APU at -O3, -Os — 2026-11-21

Branch: `pr/pgo-apu`.

**Status: none of these is on by default. Console speed of each is UNVERIFIED.** They build, and the resulting NROs ran in the Ryubing emulator with no new error kind. The emulator cannot rank them for speed (`reports/EMULATOR_TESTS_2026-11-21.md`, "Emulator noise").

The figures below come from builds that also carried `pr/cpu-guest-regs` (`.text` 22.56 MB before these variants).

## PGO (`-DMANHUNT_PGO=generate|use`)

- **generate:** every object is compiled with `-fprofile-generate -fprofile-update=single -fno-profile-values -fprofile-info-section=gcov_info`, and libgcov writes nothing at exit. Its exit path assumes a host file system, and the title ends by the auto exit or HOME.
  - `game/src/pgo_stream.c` streams every object's counters with `__gcov_info_to_gcda()` to `sdmc:/switch/manhunt1_nx/pgo/manhunt_<run>.stream`: after 60 s, every 60 s, and at the auto exit.
  - Counts only grow, so the latest snapshot of a launch holds all of it.
- **`tools/pgo_merge.py <folder of streams>`:**
  - runs `aarch64-none-elf-gcov-tool merge-stream` in the pinned devkitA64 image;
  - generate and use share `/repo/game/build/switch-pgo`, so the `.gcda` names need no rewriting, and they land in `game/build/pgo-data/`;
  - sets each `.gcda`'s object summary (runs, sum_max) as libgcov's exit path would. The stream path leaves both 0, and GCC derives its hot threshold from sum_max.
  - Streams are added together: run it on an empty profile folder.
- **use:** `-fprofile-use -fprofile-correction -fprofile-partial-training -fno-profile-values`.

**Trial in the emulator:**
- Instrumented NRO: `.text` 28.51 MB, 119 objects.
- Trained on three 240 s runs: zoo and pharm_wks (the two heaviest levels seen, started from save snapshots) and the first mission from a new game. Each snapshot took about 70 ms.
- Use build: `.text` 21.45 MB, no missing-profile warning.
- The zoo and first-mission runs had no new error kind.
- **UNVERIFIED:** whether a profile trained in the emulator steers the compiler as well as one trained on the console. Branch counts depend on the code path, not on speed, but frame pacing and timing-driven code differ.

## `MANHUNT_APU_O3` (CMake option, off)

- Compiles `apu_vp.c`, the APU voice processor, at `-O3`: GCC vectorises 14 loops instead of 6, including the mix-bin loop (`apu_vp.c:1807`) and the HRTF convolution (`apu_hrtf_fast.h:34`).
- No `-ffast-math`, and the target keeps `-ffp-contract=off`, so no float operation is reordered or fused: the output is the same bit for bit by construction. Not checked against `tests/audio-apu`.
- `apu_vp.o`: 22,339 → 38,041 bytes of code.
- The APU thread uses 40–50% of a core in the console runs of 2026-11-18.
- **Emulator:** the same binary varied from 419 to 448 ms/s of voice work across runs, so the emulator cannot show the effect.
- Changing the option does not rebuild `apu_vp.o` with the Makefile generator: delete the object or use a new build folder.

## `-Os` for the lifted code (no change needed)

- `-DMANHUNT_GEN_OPT=-Os` already exists.
- With `pr/cpu-guest-regs`: `.text` 22.56 → 19.64 MB, 24% below v1.0.0.
- Built by hand with the target's flags, `recomp_0010.c` goes from 56,427 to 47,550 instructions.
- The zoo run had no new error kind.
- Whether smaller code is faster on the Cortex-A57 (48 KB instruction cache) is what `PERF_INVESTIGATION_2026-11-16.md` item 3 left open.

## Measured and not pursued

- **Non-volatile guest stack accesses.** On `recomp_0010.c`, the 884 `esp`-relative accesses and every `PUSH32`/`POP32` were rewritten as plain loads and stores: 56,427 → 56,061 instructions (−0.65%). With `-fno-strict-aliasing`, a store through any guest pointer may alias the stack slot and the register block, so the compiler keeps reloading. Not worth the risk of a thread polling another thread's stack.
